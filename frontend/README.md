# Цепочка обмена — frontend

Клиентская часть MVP сервиса многостороннего обмена (Кейс 6, Avito Start).

Сервис объединяет пользователей в цепочку: каждый отдаёт ненужную вещь и получает нужную
(велосипед → приставка → смартфон → велосипед), без денег и без доплат. Задача фронта —
сделать эту цепочку понятной, прозрачной и безопасной на вид: человек в любой момент должен
видеть, что отдаёт, что получает, кто ещё участвует и что требуется от него сейчас.

## Стек

- **React 19** + **TypeScript** (strict, `verbatimModuleSyntax`)
- **Vite** — сборка и dev-сервер
- **TanStack Query** — серверное состояние (запросы к Go-бэкенду)
- **Zustand** — клиентское состояние
- **Tailwind v4** — стилизация; токены в стиле Avito в `@theme` (`src/index.css`)
- **oxlint** — линтер, **Prettier** — форматирование, **Vitest** — юнит-тесты
- Структура — Feature-Sliced Design (`app / pages / widgets / features / entities / shared`)

## Команды

```bash
pnpm install      # установка зависимостей
pnpm dev          # dev-сервер (http://localhost:5173)
pnpm build        # прод-сборка в dist/ (tsc -b + vite build)
pnpm test         # юнит-тесты (vitest run)
pnpm lint         # линт (oxlint)
pnpm format       # форматирование (prettier --write)
```

Пакетный менеджер — pnpm 11, закреплён в `packageManager`. `npm`/`yarn` не использовать.

## Docker

```bash
docker build -t avito-chain-front .
docker run -p 8080:80 avito-chain-front
```

Многостадийная сборка (Node → сборка, nginx → раздача статики) с SPA-fallback.
В общем `docker-compose.yml` монорепо поднимается вместе с Go-бэкендом; проксирование
`/api` на бэкенд — в `nginx.conf`.

## Как посмотреть основной сценарий

Приложение открывается сразу в личном кабинете — сервис подан как раздел внутри Авито,
а не как отдельный продукт (см. «Ключевые решения»).

1. **Мои объявления.** У объявления без обмена есть кнопка **«Готов обменять»** — это главный
   вход в сервис: обмен включается у того, что уже размещено.
2. **Что хотите взамен.** Вариантов можно указать несколько; над полями — подсказки из того,
   что человек искал и сохранял в избранное. После сохранения вещь уходит в подбор.
3. **Обмен.** Раздел с подобранными вариантами: по каждому — «Нравится» или «Не подходит»
   прямо из списка. Вариантов может быть несколько на одну вещь, и это видно в карточке.
   Бейдж у пункта «Обмен» в меню считает сделки, где ход за пользователем.
4. **Экран цепочки** — сверху что получаете и от кого, ниже схема обмена и статусы участников.
5. **«Нравится»** → обмен стартует, когда вариант устроит всех. Дальше — передача вещей
   и подтверждение получения всеми участниками.

Стоит посмотреть отдельно:

- **Конкуренция за вещь.** Лайкните вариант с велосипедом — он соберётся, а второй вариант
  с той же вещью отменится и объяснит, почему. Это наша серая зона «двойное участие».
- **Публикация нового объявления** (`/items/new`) — вторичный вход, для вещей, которые не
  продают. При загрузке фото название, категория и состояние заполняются сами.
- **Переключатель персон в шапке** («смотрю как Даша / Марк / Лена») — демо-инструмент: все трое
  участвуют в одной цепочке, поэтому один обмен можно посмотреть тремя парами глаз. В продукте
  на этом месте была бы обычная авторизация.

## Демо-ролик

фото, подбор вариантов, цепочка, передача, завершение и отказ.

Ролик собирается кодом, а не монтируется руками: [`docs/demo-source`](docs/demo-source) —
проект на Remotion, где сценарий описан данными (`src/scenes.ts`), а скриншоты снимаются

двумя командами и не расходится с продуктом.

## Данные

Фронт работает в двух режимах. Переменная `VITE_API_URL` не задана — данные берутся из
**мок-функций** в `entities/*/api`: демо открывается по ссылке без поднятого бэкенда с базой
и хранилищем. Переменная задана — те же функции ходят в реальный API.

Клиент не пишется руками, а **генерируется из общего контракта**:

```bash
pnpm api:sync     # забрать api/openapi.yaml из монорепо
pnpm api:gen      # orval → src/shared/api/generated
```

Сгенерированные типы и запросы вызываются изнутри наших api-функций, а не из компонентов:
слой маппинга (`mapItem`, `mapChain`) переводит схемы контракта в доменную модель, и экраны
о существовании бэкенда не знают.

**Что контракт (0.4.0) пока не покрывает** — работает на моках даже с подключённым бэкендом;
список собран в `shared/config/backend.ts`:

| Наше | В контракте |
| --- | --- |
| категория и состояние вещи | полей нет |
| желание списком вариантов | одна строка `wantDescription` |
| стадия передачи, отметка получения | статусы только `PENDING / ACCEPTED / REJECTED` |
| отмена варианта из-за ушедшей вещи | статуса `cancelled` нет |
| переписка, уведомления | эндпоинтов нет; SSE описан без типов событий |
| подсказки желания, распознавание фото | эндпоинтов нет |

Продуктовые решения и контракт с бэкендом — в [`docs/`](docs):
[product-flow.md](docs/product-flow.md) (пользовательский путь и почему он такой),
[api-contract.md](docs/api-contract.md) (объекты, эндпоинты, принятые решения),
[competitors.md](docs/competitors.md) (кто ещё решает эту задачу и чем мы отличаемся),
[ai-usage.md](docs/ai-usage.md) (где и как использованы нейросети).

## Материалы Авито

Раздел обмена задуман как часть кабинета Авито, поэтому оформление взято у самого Авито,
а не придумано заново. Права на эти материалы принадлежат Авито, в прототипе кейса они
использованы для наглядности:

- **Дизайн-токены** — [`docs/design-tokens`](docs/design-tokens): 2127 переменных светлой и
  тёмной тем их дизайн-системы (слои `palette` → `semantics` → `component`), сняты с рабочего
  сайта. Ядро перенесено в `@theme` в [`src/index.css`](src/index.css) — цвета, шкала кегля,
  радиусы, тени, высоты контролов.
- **Шрифт** — Manrope, тот же, что у Авито; ставится локально через `@fontsource`.
- **Иллюстрации пустых экранов** — [`public/illustrations`](public/illustrations), взяты со
  страниц «Мои объявления» и «Заказы». Там, где у Авито картинки нет (пустая выдача поиска),
  нет её и у нас.

Наша работа — раскладка экранов обмена, компоненты и логика; заимствованы оформление и графика.

## Архитектура

Feature-Sliced Design, импорты **только вниз**:
`app → pages → widgets → features → entities → shared`. Слайсы одного слоя друг друга не
импортируют, наружу — только через `index.ts`.

**Главное решение: один роут `/exchange/:id` на все состояния сделки.** Экраны «предложение /
ожидание / передача / завершение / распад» — не пять маршрутов, а один, который рендерит разное
по `chain.status × статус моего участника`. Выбор под-вида — в `widgets/chain-board/lib/selectView`,
он покрыт тестами. Код повторяет машину состояний сделки 1:1, а не размазывает её по роутам.

Ещё два места, где границы слоёв заданы намеренно:

- **`isMe` не лежит в данных.** Кто «я» — вопрос точки зрения, а не свойство цепочки: api
  проставляет флаг при чтении (`asSeenBy`). С реальной авторизацией это работает так же.
- **Реестр демо-персон — в `shared/model`,** ниже слоя сущностей: его читают мок-api в
  `entities`, а меняет фича в `features`, и обратный импорт был бы нарушением слоёв.

Сущности: `item` (объявление + желание), `chain` (цепочка, участники, состояние). Участники
денормализованы внутрь цепочки, чтобы не заводить `entities/user` ради MVP.

## Тесты

```bash
pnpm test
```

Покрыта чистая логика, от которой зависит корректность сделки:

- `widgets/chain-board/lib/selectView` — машина состояний: что показать при каждой комбинации
  статуса цепочки и статуса участника, включая невозможные;
- `entities/chain/lib/participants` — соседи по кругу, «ход за мной», подтверждение получения
  (цепочка закрывается, только когда отметили все);
- `entities/item/api` — включение обмена, отсев пустых и повторяющихся вариантов желания;
- `entities/item/api/suggestWish` — подсказки желания;
- `widgets/deals-list/lib/sortByUrgency` — порядок сделок в списке.

Компоненты не тестируем намеренно: в MVP они тонкие, вся логика вынесена в `lib` и `api`,
и юнит-тесты на неё дают больше при меньшей хрупкости, чем рендер-тесты разметки.

## Линтер

**oxlint** вместо ESLint. Обоснование: он на порядок быстрее на том же наборе правил и не тянет
за собой дерево плагинов и парсеров, а типовые проверки в проекте выполняет `tsc --strict` —
дублировать их линтером не требуется. Конфигурация — `.oxlintrc.json`.

Включены плагины `react`, `typescript`, `oxc`. Явно подняты до `error`:

- `react/rules-of-hooks` — нарушение правил хуков даёт баги, которые не ловятся типами;
- `react/only-export-components` — держит границу public API слайсов и не ломает fast refresh.

Форматирование вынесено в Prettier (`.prettierrc.json`), чтобы стиль не спорил с правилами
линтера. Проверка формата — `pnpm format:check`.

## Использование нейросетей

Требование кейса — указать прозрачно.

- **В продукте.** Подсказки желания (`entities/item/api/suggestWish`) — **эвристика, не модель**:
  берутся поиски и избранное пользователя, из них оставляются только те, которым соответствуют
  реально существующие объявления других участников, дальше добор по категории отдаваемой вещи.
  Задача — снять трение в том месте, где оно осталось: вещи внутри Авито уже описаны, а вот
  «что хочу взамен» человек формулирует размыто, и из размытого желания граф не строится.
  Функция сознательно оформлена как единственная точка входа: при подключении реальной модели
  меняется её тело, интерфейс и форма остаются прежними.
- **В продукте.** Распознавание вещи по фото (`entities/item/api/recognizeItem`) — **заглушка**
  под реальную модель: при загрузке фото в новом объявлении (`/items/new`) заполняются название,
  категория и состояние, любое поле правится руками. Узнаёт демо-фотографии по имени файла,
  на остальных честно сообщает, что не распознала, и форма заполняется как обычно.
  У главного входа — обмена у уже размещённого объявления — распознавать нечего: поля там заполнены.
  При подключении бэкенда поведение меняется: модель отдаёт категорию, состояние и описание,
  но не название, и результат показывается **подсказкой рядом с полями**, а не переписывает форму —
  запрос идёт во внешний API и занимает больше секунды ([`docs/ai-usage.md`](docs/ai-usage.md)).
- **В разработке.** Claude Code использовался для написания и ревью кода, генерации юнит-тестов
  и проработки продуктовых решений. Все решения проверялись и принимались автором; каждый шаг
  проходил `pnpm test`, `pnpm lint` и `pnpm build`.

## Ограничения MVP

Сознательно не сделано, чтобы не размывать основную механику:

- **никаких денег** — ни цен в интерфейсе обмена, ни доплат: кейс требует формата сделки без
  денежных затрат, а обмен работает именно потому, что субъективная ценность вещи не равна
  рыночной цене. Соразмерность обеспечивается тем, что цепочка собирается, только когда желание
  каждого удовлетворено;
- **замена участника без развала цепочки** — отказ распускает цепочку целиком, вещи
  разблокируются. Экран для состояния «я вышел, остальные ищут замену» спроектирован, но
  включается только вместе с поддержкой на бэкенде;
- **реалтайм в переписке** — сам чат есть (раздел «Сообщения», разговор по каждой вещи), но
  сообщения не приходят сами: в MVP хватает refetch по TanStack Query. Ответ собеседника
  в демо приходит сразу — заготовленной репликой по смыслу вопроса;
- **стоп-листы «чего не хочу», веса вариантов, обучение на отказах** — усложняют модель желания,
  не влияя на основную механику;
- **авторизация** — вместо неё демо-переключатель персон.
