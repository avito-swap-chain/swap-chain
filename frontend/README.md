# Цепочка обмена — frontend

Клиентская часть MVP сервиса многостороннего обмена (Кейс 6, Avito Start).

Сервис объединяет пользователей в цепочку: каждый отдаёт ненужную вещь и получает нужную
(велосипед → приставка → смартфон → велосипед), без денег и без доплат. Задача фронта —
сделать эту цепочку понятной, прозрачной и безопасной на вид: человек в любой момент должен
видеть, что отдаёт, что получает, кто ещё участвует и что требуется от него сейчас.

**Это личный репозиторий с моей частью работы — клиентом целиком.** Командный проект (этот
фронт + Go-бэкенд + инфраструктура) живёт отдельно:
[avito-swap-chain/swap-chain](https://github.com/avito-swap-chain/swap-chain). Фронт уезжает
туда через `git subtree` — со всей историей коммитов, а не одним «add frontend»
([PR #5](https://github.com/avito-swap-chain/swap-chain/pull/5) и далее).

Минутный ролик пути пользователя — [`docs/demo.mp4`](docs/demo.mp4).

## Стек

- **React 19** + **TypeScript** (strict, `verbatimModuleSyntax`)
- **Vite** — сборка и dev-сервер
- **TanStack Query** — серверное состояние (запросы к Go-бэкенду)
- **Zustand** — клиентское состояние
- **Tailwind v4** — стилизация; токены в стиле Avito в `@theme` (`src/index.css`)
- **oxlint** — линтер, **Prettier** — форматирование, **Vitest** + **Testing Library** — тесты
- Структура — Feature-Sliced Design (`app / pages / widgets / features / entities / shared`)

## Команды

```bash
pnpm install      # установка зависимостей
pnpm dev          # dev-сервер (http://localhost:5173)
pnpm build        # прод-сборка в dist/ (tsc -b + vite build)
pnpm test         # юнит-тесты (vitest run)
pnpm lint         # линт (oxlint)
pnpm format       # форматирование (prettier --write)
```

Пакетный менеджер — pnpm 11, закреплён в `packageManager`. `npm`/`yarn` не использовать.

## Где это работает

Два адреса, и роли у них разные.

**Демо на GitHub Pages** — [merely04.github.io/barter-ring-frontend](https://merely04.github.io/barter-ring-frontend/).
Собирается на мок-данных, поэтому открывается всегда, даже когда стенд бэкенда лежит.
Это витрина: посмотреть продукт, ничего не поднимая.

**Контейнер рядом с бэкендом** — рабочая сборка против живого API:

```bash
docker compose up frontend        # в монорепо: фронт на ${FRONTEND_PORT:-18080}
```

Многостадийная сборка (Node → сборка, nginx → раздача статики) с SPA-fallback. Образ собирается
с `VITE_API_URL=/`: фронт запрашивает `/api/…` у своего же nginx, а тот проксирует на `backend:8080`.

**Адрес API относительный не для красоты.** Переменная попадает в бандл на этапе сборки, поэтому
абсолютный `http://localhost:18080` в браузере пользователя указывал бы на его собственную машину.
Плюс общий origin снимает две проблемы разом: сессия живёт в куке с `SameSite=Lax` и в
кросс-доменный запрос не попадёт, а CORS с `credentials` пришлось бы настраивать отдельно.

Для потока событий (`/api/v1/events`) в прокси отключена буферизация и поднят таймаут — иначе
SSE копится в буфере и подписка рвётся через минуту.

## Как посмотреть основной сценарий

Приложение открывается сразу в личном кабинете — сервис подан как раздел внутри Авито,
а не как отдельный продукт (см. «Ключевые решения»).

1. **Мои объявления.** У объявления без обмена есть кнопка **«Готов обменять»** — это главный
   вход в сервис: обмен включается у того, что уже размещено.
2. **Что хотите взамен.** Вариантов можно указать несколько; над полями — подсказки из того,
   что человек искал и сохранял в избранное. После сохранения вещь уходит в подбор.
3. **Обмен.** Раздел с подобранными вариантами: по каждому — «Нравится» или «Не подходит»
   прямо из списка. Вариантов может быть несколько на одну вещь, и это видно в карточке.
   Бейдж у пункта «Обмен» в меню считает сделки, где ход за пользователем.
4. **Экран цепочки** — сверху что получаете и от кого, ниже схема обмена и статусы участников.
5. **«Нравится»** → обмен стартует, когда вариант устроит всех. Дальше — передача вещей
   и подтверждение получения всеми участниками.

Стоит посмотреть отдельно:

- **Конкуренция за вещь.** Лайкните вариант с велосипедом — он соберётся, а второй вариант
  с той же вещью отменится и объяснит, почему. Это наша серая зона «двойное участие».
- **Публикация нового объявления** (`/items/new`) — вторичный вход, для вещей, которые не
  продают. Загруженное фото уходит на разбор модели: она предлагает описание, категорию
  и состояние отдельным блоком, применяет их человек кнопкой. Названия модель не даёт.
- **Правка объявления.** На карточке вещи в подборе — карандаш: название, описание, категория
  и желание меняются без выхода из подбора. Отдельное действие именно потому, что снятие
  отменяет предложения с этой вещью у других людей, а уточнить формулировку — обычное дело.
- **Снятие вещи с обмена** живёт на том же экране правки, под формой: желание убирается, вещь
  возвращается в обычные объявления, а предложения с ней отменяются. Это не удаление — вещь
  остаётся в истории завершённых обменов. На карточке действия нет намеренно: там его
  задевали мимоходом, хотя цена у него чужая.
- **Рабочее место сотрудника ПВЗ** (`/admin/deliveries`, только у роли `ADMIN`) — доставки
  собравшихся цепочек и их продвижение по статусам. Без него обмен не закрывается: подтвердить
  получение можно только после того, как вещь ушла в доставку.
- **Уведомления** (`/notifications` и счётчик в шапке) — приходят с сервера событием в поток
  и переживают перезагрузку страницы: многосторонняя сделка идёт не в один сеанс, и человек
  должен узнать, что ход за ним, не сидя во вкладке.
- **Мои отзывы** (`/reviews`) — отдельный раздел меню, как у Авито: вкладка «Ждут оценки»
  собирает завершённые обмены и даёт оценить соседа прямо в строке, вкладка «Обо мне» —
  то, что написали о самом человеке. В обмене рейтинг это единственный довод о незнакомце,
  и прятать его в чужой профиль неправильно.
- **Чёрный список** (`/blocked`) — вторая половина блокировки: заблокировать человека можно
  из его профиля, а посмотреть и снять блокировку — здесь. Пока раздела не было, список жил
  только на бэкенде и молча влиял на подбор.
- **Профиль** — свой с правкой имени и аватара, чужой открывается из цепочки: обмен сводит
  незнакомых людей, и посмотреть, с кем имеешь дело, нужно до согласия.
- **Плавающий мессенджер** в правом нижнем углу — как у Авито: переписка догоняет человека
  на любой странице кабинета. Спросить о вещи можно до ответа на предложение, и ответ приходит,
  пока человек смотрит цепочку.
- **Переключатель аккаунтов в шапке** («смотрю как…») — демо-инструмент: цепочку из трёх
  участников иначе не показать по одной ссылке. С подключённым бэкендом он делает настоящие
  выход и вход, а не подменяет данные.

## Данные

Фронт работает в двух режимах. Переменная `VITE_API_URL` не задана — данные берутся из
**мок-функций** в `entities/*/api`: демо открывается по ссылке без поднятого бэкенда с базой
и хранилищем. Переменная задана — те же функции ходят в реальный API.

Клиент не пишется руками, а **генерируется из общего контракта**:

```bash
pnpm api:sync     # забрать api/openapi.yaml из монорепо
pnpm api:gen      # orval → src/shared/api/generated
```

Сгенерированные типы и запросы вызываются изнутри наших api-функций, а не из компонентов:
слой маппинга (`mapItem`, `mapChain`) переводит схемы контракта в доменную модель, и экраны
о существовании бэкенда не знают.

**Что контракт (0.8.0) пока не покрывает** — работает на моках даже с подключённым бэкендом;
список собран в `shared/config/backend.ts`:

| Наше                                 | В контракте                                                         |
| ------------------------------------ | ------------------------------------------------------------------- |
| состояние вещи                       | поля нет                                                            |
| фото в правке объявления             | `imageUrls` в `UpdateItemRequest` не принимается                    |
| отмена варианта из-за ушедшей вещи   | статуса `cancelled` нет                                             |
| служебный канал «Авито Обмен» в чате | отправитель сообщения — всегда пользователь                         |
| подсказки желания                    | эндпоинта нет — и модели тоже: это эвристика на поисках и избранном |

**Вход — по одному телефону, без пароля:** его нет в контракте, бэкенд выдаёт сессию в обмен
на номер и держит её в куке (`POST /api/v1/session` при входе, `POST /api/v1/users` при
регистрации). Незнакомый номер не ошибка, а развилка: бэкенд отвечает 404, и форма дорисовывает
поле имени вместо отдельного экрана регистрации. На моках сессии нет — там «я» это выбранная
персона, поэтому демо по ссылке открывается сразу в кабинете.

Продуктовые решения и контракт с бэкендом — в [`docs/`](docs):
[product-flow.md](docs/product-flow.md) (пользовательский путь и почему он такой),
[api-contract.md](docs/api-contract.md) (объекты, эндпоинты, принятые решения),
[competitors.md](docs/competitors.md) (кто ещё решает эту задачу и чем мы отличаемся),
[ai-usage.md](docs/ai-usage.md) (где и как использованы нейросети).

## Материалы Авито

Раздел обмена задуман как часть кабинета Авито, поэтому оформление взято у самого Авито,
а не придумано заново. Права на эти материалы принадлежат Авито, в прототипе кейса они
использованы для наглядности:

- **Дизайн-токены** — [`docs/design-tokens`](docs/design-tokens): 2127 переменных светлой и
  тёмной тем их дизайн-системы (слои `palette` → `semantics` → `component`), сняты с рабочего
  сайта. Ядро перенесено в `@theme` в [`src/index.css`](src/index.css) — цвета, шкала кегля,
  радиусы, тени, высоты контролов.
- **Шрифт** — Manrope, тот же, что у Авито; ставится локально через `@fontsource`.
- **Иллюстрации пустых экранов** — [`public/illustrations`](public/illustrations), взяты со
  страниц «Мои объявления» и «Заказы». Там, где у Авито картинки нет (пустая выдача поиска),
  нет её и у нас.

Наша работа — раскладка экранов обмена, компоненты и логика; заимствованы оформление и графика.

## Архитектура

Feature-Sliced Design, импорты **только вниз**:
`app → pages → widgets → features → entities → shared`. Слайсы одного слоя друг друга не
импортируют, наружу — только через `index.ts`.

**Главное решение: один роут `/exchange/:id` на все состояния сделки.** Экраны «предложение /
ожидание / передача / завершение / распад» — не пять маршрутов, а один, который рендерит разное
по `chain.status × статус моего участника`. Выбор под-вида — в `widgets/chain-board/lib/selectView`,
он покрыт тестами. Код повторяет машину состояний сделки 1:1, а не размазывает её по роутам.

Ещё два места, где границы слоёв заданы намеренно:

- **`isMe` не лежит в данных.** Кто «я» — вопрос точки зрения, а не свойство цепочки: api
  проставляет флаг при чтении (`asSeenBy`). С реальной авторизацией это работает так же.
- **Реестр демо-персон — в `shared/model`,** ниже слоя сущностей: его читают мок-api в
  `entities`, а меняет фича в `features`, и обратный импорт был бы нарушением слоёв.

Сущности: `item` (объявление + желание), `chain` (цепочка, участники, состояние). Участники
денормализованы внутрь цепочки, чтобы не заводить `entities/user` ради MVP.

## Тесты

```bash
pnpm test
```

Покрыта чистая логика, от которой зависит корректность сделки:

- `widgets/chain-board/lib/selectView` — машина состояний: что показать при каждой комбинации
  статуса цепочки и статуса участника, включая невозможные;
- `entities/chain/lib/participants` — соседи по кругу, «ход за мной», подтверждение получения
  (цепочка закрывается, только когда отметили все);
- `entities/item/api` — включение обмена, правка объявления, отсев пустых и повторяющихся
  вариантов желания;
- `entities/item/api/suggestWish` — подсказки желания;
- `entities/message` — склейка ленты реплик и идемпотентность отправки;
- `shared/lib/phone` — разбор телефона: `8…`, `+7…` и запись без кода страны это один номер;
- `widgets/deals-list/lib/sortByUrgency` — порядок сделок в списке.

**Экраны покрыты точечно** — там, где ошибались на самом деле, а не для галочки:

- `pages/login` — развилка на регистрацию у незнакомого номера; демо-кнопка входит, а не
  регистрирует (регрессия: признак «новый пользователь» читался из замыкания и залипал после
  неудачной попытки); кривой номер не уходит на бэкенд; `8…` и `+7…` — один и тот же человек;
- `features/switch-persona` — свой аккаунт остаётся в списке, когда смотришь чужими глазами.
  Ровно это нашёл ментор: зарегистрировался своим номером, переключился на демо-аккаунт —
  и вернуться было нечем.

Остальные компоненты не тестируем: они тонкие, вся логика вынесена в `lib` и `api`, и юнит-тесты
на неё дают больше при меньшей хрупкости, чем рендер-тесты разметки. Браузерное окружение
включается построчно (`// @vitest-environment jsdom`) в самих тестах экранов — логических
тестов на порядок больше, и поднимать им jsdom не за что.

## Линтер

**oxlint** вместо ESLint. Обоснование: он на порядок быстрее на том же наборе правил и не тянет
за собой дерево плагинов и парсеров, а типовые проверки в проекте выполняет `tsc --strict` —
дублировать их линтером не требуется. Конфигурация — `.oxlintrc.json`.

Включены плагины `react`, `typescript`, `oxc`. Явно подняты до `error`:

- `react/rules-of-hooks` — нарушение правил хуков даёт баги, которые не ловятся типами;
- `react/only-export-components` — держит границу public API слайсов и не ломает fast refresh.

Форматирование вынесено в Prettier (`.prettierrc.json`), чтобы стиль не спорил с правилами
линтера. Проверка формата — `pnpm format:check`.

## Использование нейросетей

Требование кейса — указать прозрачно.

- **В продукте.** Подсказки желания (`entities/item/api/suggestWish`) — **эвристика, не модель**:
  берутся поиски и избранное пользователя, из них оставляются только те, которым соответствуют
  реально существующие объявления других участников, дальше добор по категории отдаваемой вещи.
  Задача — снять трение в том месте, где оно осталось: вещи внутри Авито уже описаны, а вот
  «что хочу взамен» человек формулирует размыто, и из размытого желания граф не строится.
  Функция сознательно оформлена как единственная точка входа: при подключении реальной модели
  меняется её тело, интерфейс и форма остаются прежними.
- **В продукте.** Распознавание вещи по фото (`entities/item/api/recognizeItem`) — **настоящая
  модель на бэкенде**: при загрузке фото в новом объявлении (`/items/new`) она отдаёт описание
  в стиле объявления, категорию и состояние. Названия не даёт намеренно — угаданный бренд
  вместо настоящего вредит, по названию потом ищут обмен. Результат приходит **асинхронно**:
  `POST /vision/analyze` отвечает `202`, а сам разбор прилетает событием в поток `/events`,
  поэтому анализ запускается только после того, как поток установлен. Ожидание занимает
  до полуминуты и поэтому забирает экран целиком: шаги проговариваются вслух — «Загружаем
  фото», «Подключаем нейросеть», «Модель разбирает фото», — и это **настоящие шаги**
  разбора, а не прогресс на таймере; из ожидания есть выход, дальше поля заполняются руками.
  Результат показывается **предложением** с кнопкой «Заполнить этим», а не переписывает
  объявление сам: заполняются только пустые поля, набранное человеком модель не трогает.
  Без бэкенда остаётся заглушка по имени файла, чтобы демо открывалось по ссылке
  ([`docs/ai-usage.md`](docs/ai-usage.md)).
- **В разработке.** Claude Code использовался для написания и ревью кода, генерации юнит-тестов
  и проработки продуктовых решений. Все решения проверялись и принимались автором; каждый шаг
  проходил `pnpm test`, `pnpm lint` и `pnpm build`.

## Что здесь моё

Клиент сервиса целиком — от продуктового сценария до вёрстки, тестов и сборки, плюс
продуктовая документация в [`docs/`](docs). Что за этим стоит:

- **Продуктовые решения, а не только вёрстка.** Обмен подан атрибутом существующего
  объявления, а не отдельным сервисом; параллельный подбор нескольких вариантов на одну вещь
  с отменой конкурентов; отказ от цен и доплат в интерфейсе. Гипотезы, серые зоны и
  обоснования — в [`docs/product-flow.md`](docs/product-flow.md).
- **Машина состояний сделки на одном роуте.** Пять состояний цепочки — не пять маршрутов,
  а `chain.status × статус участника`; выбор вида покрыт тестами, включая невозможные
  комбинации.
- **Дизайн-система Авито, снятая с рабочего сайта,** а не подобранная на глаз: 2127 токенов,
  геометрия компонентов, обе их вёрстки — десктопный кабинет и мобильная с нижней панелью.
- **Контракт с бэкендом.** [`docs/api-contract.md`](docs/api-contract.md) написан со стороны
  фронта и обоснован по каждому решению; клиент генерируется из общего `openapi.yaml` через
  orval, расхождения контракта с продуктом зафиксированы, а не замолчаны.
- **Демо-ролик собирается кодом** ([`docs/demo-source`](docs/demo-source), Remotion):
  сценарий описан данными, скриншоты снимаются скриптом с живого фронта — после правок
  интерфейса ролик пересобирается двумя командами и не расходится с продуктом.

## Ограничения MVP

Сознательно не сделано, чтобы не размывать основную механику:

- **никаких денег** — ни цен в интерфейсе обмена, ни доплат: кейс требует формата сделки без
  денежных затрат, а обмен работает именно потому, что субъективная ценность вещи не равна
  рыночной цене. Соразмерность обеспечивается тем, что цепочка собирается, только когда желание
  каждого удовлетворено;
- **замена участника без развала цепочки** — отказ распускает вариант целиком, вещи
  разблокируются и возвращаются в подбор. Замену вышедшему не ищем осознанно: при длине
  в три участника собрать новый вариант с нуля дешевле, чем латать старый, и часть тех же
  людей в него обычно попадает снова;
- **вложения, правка и удаление сообщений** — переписка только текстовая: вопрос о состоянии
  вещи задаётся словами, а всё остальное усложняет и фронт, и модерацию. Новые сообщения при
  этом приходят сами — long-poll'ом, как отдаёт их контракт. На моках ответ собеседника
  приходит сразу, заготовленной репликой по смыслу вопроса;
- **стоп-листы «чего не хочу», веса вариантов, обучение на отказах** — усложняют модель желания,
  не влияя на основную механику;
- **регистрация со сложным профилем** — вход по одному телефону, без пароля и подтверждения:
  сессию выдаёт бэкенд в обмен на номер, и для MVP этого достаточно.
