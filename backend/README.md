# Backend

Go backend содержит модули `modules/analyze`, `modules/matching`,
`modules/chat`, `modules/admin`, HTTP-транспорт, подключение к PostgreSQL и
версионируемые миграции. Основная точка входа — `cmd/api`, служебная точка входа
для схемы данных — `cmd/migrate`.

## Локальный запуск без Docker для Go

Сначала запустите PostgreSQL/pgvector и примените миграции из корня репозитория:

```bash
docker compose up -d postgres
make migrate-up
make run-backend
```

По умолчанию backend слушает `:8080`, а локальное подключение использует
`postgres://swap_chain:swap_chain@127.0.0.1:5432/swap_chain?sslmode=disable`.
Настройки переопределяются переменными из корневого `.env.example`.

## Команды

Из директории `backend/` доступны эквиваленты целей Makefile:

```bash
go run ./cmd/migrate up
go run ./cmd/migrate down
go run ./cmd/migrate version
go run ./cmd/api
go test ./...
go build ./...
```

Миграция `000001` создаёт расширение pgvector, таблицы `users`, `items`,
`chains`, `chain_items`, enum-типы статусов, внешние ключи и индексы. Размерность
embedding зафиксирована как `vector(1024)` под текущую модель `bge-m3`.

Миграция `000005` добавляет метаданные анализа и индекс восстановления зависших
карточек. Полный pipeline оценивает описание, сохраняет выбранную пользователем
offer-категорию, определяет категории пожеланий и записывает embeddings одним
атомарным обновлением перед переходом в `MATCHING`.

Миграция `000006` добавляет минимальный demo flow ПВЗ. Только пользователь с
ролью `ADMIN` видит передачи принятых цепочек и последовательно переводит товар
`AWAITING_PVZ → AT_PVZ → IN_DELIVERY`; повтор текущего перехода идемпотентен.
Эта же миграция создаёт зарезервированную demo-учётку
`ПВЗ Администратор (demo)` / `+79009999999`, которая входит через обычный
`POST /api/v1/session` без пароля.

Миграция `000007` добавляет личные диалоги между соседями обменного кольца,
доступные сразу после сохранения подобранной цепочки, включая статус `PENDING`.
Миграция `000026` переводит адресацию на `itemId + counterpartId`: одна и та же
передаваемая вещь с той же парой пользователей имеет единую историю независимо
от числа цепочек. Сообщения сохраняются идемпотентно по `clientMessageId`.
`GET /api/v1/chat/threads` одним запросом возвращает уникальные диалоги по вещам,
которые пользователь получает. Собственные отдаваемые вещи появляются только
после первого сообщения, чтобы их владелец мог ответить. Ответ также содержит
краткие данные вещи, последние сообщения и счётчики непрочитанного. История
поддерживает long-poll до 25 секунд, а read-watermark не может сдвинуться назад.
PostgreSQL —
источник истины; in-memory notifier только пробуждает long-poll внутри текущего
процесса. При переходе к нескольким экземплярам backend notifier потребуется
заменить на межпроцессный сигнал.

Миграция `000008` завершает физический flow: администратор может перевести
конкретную передачу `IN_DELIVERY → RECEIVED`, а получатель подтверждает свою
единственную входящую вещь через `POST /api/v1/chains/{chainId}/receipt`.
Получатель берётся только из opaque session и повторное подтверждение
идемпотентно. Строка цепочки блокируется на время транзакции; последняя из двух
или трёх передач атомарно переводит `ACCEPTED → COMPLETED`. Вещи остаются
`LOCKED` как защита от повторного matching до введения отдельного статуса
`EXCHANGED`.

Миграция `000010` удаляет дублирующие embedding-поля, делает `image_amount`
вычисляемым из массива изображений и добавляет системные категории. При старте
backend проверяет наличие моделей Ollama и рассчитывает только отсутствующие
embeddings категорий в пределах `ANALYSIS_BOOTSTRAP_TIMEOUT`.

Миграция `000011` добавляет `matching_jobs` и backfill существующих
`MATCHING`-вещей. Успешный analyze атомарно ставит задание вместе с переходом
в `MATCHING`. Фоновый worker находит ещё не сохранённые циклы и создаёт через
chain service предложения `PENDING`; уникальный `cycle_key` делает повторную
обработку и конкурентный запуск безопасными.

Миграция `000020` добавляет состояние `ACTION_REQUIRED` и сохраняет все
доступные категории для ручного выбора каждого wish. Категорию offer пользователь обязан
выбрать при создании карточки, и analyze её не классифицирует и не
перезаписывает. Для текстов пожеланий analyze сначала использует Flash, затем
embedding fallback. Если fallback неоднозначен, matching не запускается до
атомарного выбора владельца через
`POST /api/v1/items/{itemId}/category-decision`.

HTTP API предоставляет liveness `GET /health`, readiness `GET /api/v1/health`
и `GET /items/{itemID}/matching`, запускающий существующий matching engine через
sqlc-запрос к PostgreSQL. Публичный контракт находится в `../api/openapi.yaml`.
